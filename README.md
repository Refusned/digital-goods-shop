# Магазин цифровых товаров

Тестовое задание «Фуллстек разработчик», **первый и второй этап в одном репозитории**.

Первый этап: витрина по макету, покупка с автоматической выдачей ключа, однократная выдача
под гонками, восстановление после сбоев, промокоды с лимитом.

Второй этап (поверх первого, без переписывания):

* **живая витрина**: цены и наличие меняются у всех открытых вкладок сразу, без перезагрузки;
* **честная покупка последней единицы**: ключ бронируется ДО оплаты, победитель один,
  проигравший получает понятный отказ и ничего не платит;
* **бронь с таймером**: обратный отсчёт на экране, по истечении товар возвращается в продажу всем;
* **устойчивость покупки**: двойной клик, «Назад», обновление страницы и обрыв связи не создают
  второго заказа и не задваивают платёж;
* **мгновенный поиск** по каталогу в тысячи позиций с фильтрами, которые живут в адресе страницы.

Стек: HTML, CSS и JavaScript без фреймворков на фронте; Node.js 20+ (ESM), Express и PostgreSQL 16 на бэкенде.
Из зависимостей только `express` и `pg`, тесты на встроенном `node:test`.

## Запуск

```bash
docker compose up -d          # PostgreSQL на localhost:5443
cp .env.example .env
npm install
npm run migrate
npm run migrate               # применяет только новые миграции, учёт в schema_migrations
npm run seed                  # каталог, пул ключей и промокоды из задания
npm run seed -- --bulk=5000   # плюс синтетический каталог для проверки поиска
npm start                     # http://localhost:3020
```

Открыть: витрина `http://localhost:3020`, админка `http://localhost:3020/admin.html` (токен `admin-token` из `.env`).
Postgres можно взять свой, достаточно поправить `DATABASE_URL`.

Полностью в Docker, без локального Node:

```bash
docker compose --profile app up -d --build
docker compose --profile app exec app node scripts/migrate.js
docker compose --profile app exec app node scripts/seed.js
```

## Проверка

```bash
npm test        # 68 тестов: оба этапа целиком
npm run race    # 9 сценариев приёмки первого этапа против ЗАПУЩЕННОГО сервера
npm run stage2  # 21 сценарий приёмки второго этапа против ЗАПУЩЕННОГО сервера
```

Тесты второго этапа: `test/05-live-storefront` (живая витрина), `test/06-last-unit-race`
(гонка за последнюю единицу), `test/07-reservation` (бронь с таймером),
`test/08-purchase-resilience` (устойчивость покупки), `test/09-search` (поиск по большому каталогу).

`npm test` работает сразу после `docker compose up -d`: скрипт `scripts/test.js` создаёт отдельную
базу `<имя>_test`, накатывает миграции и только потом запускает прогон уже с этой базой.
Тестовые файлы дополнительно отказываются стартовать на невыделенной базе, поэтому рабочие данные
они стереть не могут. Своя база задаётся через `TEST_DATABASE_URL`.

⚠️ `npm run race` меняет данные: создаёт заказы, расходует ключи из пула и сбрасывает счётчики
промокодов. Поэтому он требует явного подтверждения и запускается как
`ALLOW_DESTRUCTIVE_RACE=1 npm run race` на демонстрационной базе, а не на той, где лежит что-то ценное.

### Как воспроизвести проверку гонок

Самый короткий путь: `npm run race`. Он проверяет ровно те сценарии, что перечислены в задании, и печатает результат по каждому.

Вручную, 50 параллельных вебхуков по одному заказу:

```bash
ORDER=$(curl -s -XPOST localhost:3020/api/orders -H 'content-type: application/json' \
        -d '{"sku":"KEY-CS2-PRIME"}' | python3 -c 'import sys,json;print(json.load(sys.stdin)["id"])')

seq 50 | xargs -P 50 -I{} curl -s -XPOST localhost:3020/webhook/payment \
  -H 'content-type: application/json' \
  -d "{\"event_id\":\"evt_{}\",\"order_id\":\"$ORDER\",\"status\":\"paid\",\"amount\":1290,\"currency\":\"RUB\",\"created_at\":\"2026-01-01T12:00:00Z\"}" > /dev/null

curl -s localhost:3020/api/orders/$ORDER      # delivered, ровно один код
```

Промокод под гонкой (лимит 3, двадцать одновременных заказов):

```bash
seq 20 | xargs -P 20 -I{} curl -s -XPOST localhost:3020/api/orders \
  -H 'content-type: application/json' -d '{"sku":"KEY-GTA5","promocode":"LIMIT3"}' | grep -c '"promocode":"LIMIT3"'
# 3
```

## Как обеспечена однократная выдача

Тремя ограничениями базы, а не аккуратностью кода:

* частичный уникальный индекс `stock_keys (order_id) WHERE order_id IS NOT NULL`: один заказ не может получить два ключа;
* уникальный индекс `stock_keys (code)`: один и тот же код нельзя завезти дважды, в том числе в разные товары;
* захват ключа идёт условным `UPDATE ... FOR UPDATE SKIP LOCKED`, поэтому два заказа не могут забрать одну строку.

Сверху этого: `pg_advisory_xact_lock` по заказу разводит параллельные попытки выдачи,
`FOR UPDATE SKIP LOCKED` разводит конкуренцию разных заказов за свободные ключи,
`payment_events.event_id PRIMARY KEY` делает повтор вебхука безопасным,
а `Idempotency-Key` при создании заказа гасит двойной клик по кнопке «Купить»
(вместе с ключом хранится отпечаток запроса из `sku`, промокода и `order_id`:
тот же ключ с другими параметрами даёт 409, а не чужой заказ).

Подробнее в [NOTES.md](NOTES.md).

## Что работает на витрине

Верстка сделана по макету структурно: шапка, баннер, ряд иконок сервисов, блок пополнения Steam, ряд карточек.
Отзывы и футер по заданию не верстались. Пять точек интерактива:

1. **Баннер-карусель**: автопрокрутка каждые 5 секунд, стрелки, активные точки-индикаторы, пауза при наведении.
2. **Кнопка «Каталог»**: открывает выпадающее меню, повторный клик, клик вне меню и Esc его закрывают.
3. **Переключатель валют** в блоке пополнения Steam: меняет активное состояние, пересчёта нет (как в задании).
4. **Иконки сервисов**: плавное выделение при наведении.
5. **Карточки товара**: подъём, тень и обводка при наведении.

Поле «Логин Steam» оставлено как в макете и никуда не отправляется. Промокод раскрывается по кнопке
«Ввести промокод» и проверяется на сервере до покупки.

## Флоу покупки

`Купить` → заказ создан (`created`) → страница статуса → кнопка `Оплатить` шлёт вебхук по контракту
на наш же эндпоинт → `paid` → автоматическая выдача ключа из пула → `delivered`, код на экране.

Кнопка «Оплата не прошла» переводит заказ в `payment_failed`. Использование промокода при этом
НЕ возвращается в лимит: освобождение по неуспешной оплате открывает обход лимита,
подробности в [NOTES.md](NOTES.md).

## API

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/catalog?section=&limit=` | витрина с остатками |
| `POST` | `/api/promo/quote` | предпросмотр скидки, код не расходуется |
| `POST` | `/api/orders` | создать заказ. Тело: `{ "sku", "promocode"?, "order_id"? }`, заголовок `Idempotency-Key` |
| `GET` | `/api/orders/:id` | заказ со статусом и кодом |
| `POST` | `/api/orders/:id/simulate-payment` | эмуляция оплаты: шлёт вебхук `paid` или `failed` |
| `POST` | `/webhook/payment` | вебхук платёжной системы по контракту из задания |
| `GET` | `/api/admin/reconciliation` | сверка, остатки, промокоды, баланс журнала денег |
| `POST` | `/api/admin/orders/:id/deliver` | ручная повторная выдача (идемпотентна) |
| `POST` | `/api/admin/stock/:sku/restock` | завоз ключей в пул |

Админские ручки закрыты заголовком `X-Admin-Token` (значение из `.env`).
Выдача идёт из локального пула ключей: внешнего поставщика в контуре этого задания нет,
контракт поставщика из приложения к ТЗ здесь не используется.
`order_id` в `POST /api/orders` нужен для сценария «вебхук пришёл раньше заказа»: платёжная система
может знать идентификатор заказа раньше нас.


## Второй этап

### Живая витрина

Источник событий это сама база: триггеры на `products` и `stock_keys` шлют `NOTIFY`, сервер держит
одно постоянное соединение с `LISTEN` и раздаёт изменения открытым вкладкам через Server-Sent Events.
Прикладной код, который «не забыл разослать событие», работает только пока о нём все помнят,
а витрина обязана оставаться правдивой и при ручном `UPDATE`, и при миграции, и при второй копии сервиса.

Вкладка обновляет только изменившиеся карточки, поэтому список не мигает. После обрыва связи
браузер переподключается сам, и витрина догоняет пропущенное полным снимком: события за время
обрыва не восстанавливаются, а состояние восстанавливается.

**Как воспроизвести**

```bash
# 1. открыть http://localhost:3020 в двух вкладках
# 2. поменять цену в обход приложения
psql postgres://shop:shop@localhost:5443/shop -c \
  "UPDATE products SET price_minor = 777 WHERE sku = 'KEY-CS2-PRIME'"
# 3. в обеих вкладках цена меняется сама, изменение подсвечивается
```

Наличие проверяется так же: любой заказ на товар занимает ключ, и остаток гаснет у всех.
Индикатор рядом с поиском показывает состояние канала: зелёный это живые данные,
жёлтый это потеря связи и переподключение.

### Покупка последней единицы наперегонки

Ключ бронируется в момент оформления, **до оплаты**. Это и есть развязка гонки: победитель уходит
на оплату, проигравший сразу получает `409 sold_out` и понятное сообщение, а денег с него никто
не брал. Обратный порядок (сначала деньги, потом поиск ключа) неизбежно рождает оплаченные заказы
без товара.

Гонку разводит база: `UPDATE ... FOR UPDATE SKIP LOCKED` не даёт двум оформлениям встать в очередь
на одну строку, а частичный уникальный индекс `stock_keys (reserved_by_order)` не даёт одному заказу
держать два ключа.

**Как воспроизвести**

```bash
# товар с единственным ключом, два покупателя одновременно
seq 2 | xargs -P 2 -I{} curl -s -o /dev/null -w "%{http_code}\n" \
  -XPOST localhost:3020/api/orders -H 'content-type: application/json' \
  -d '{"sku":"KEY-CS2-PRIME"}'
# 201 и 409
```

То же самое с проверками: `ALLOW_DESTRUCTIVE_RACE=1 npm run stage2`.

### Бронь с таймером

На странице оформления идёт обратный отсчёт. Он считается от **серверного** времени
(`server_time` приходит рядом с `reserved_until`): часы браузера могут отличаться на минуты,
и показывать по ним чужое время нельзя.

Если оплата не пришла вовремя, бронь снимается, заказ становится `expired`, товар возвращается
в продажу для всех, и живой канал сообщает об этом открытым вкладкам. Оплата, пришедшая с опозданием,
не теряется: заказ попробует получить любой свободный ключ, а если ключей нет, останется
в восстановимом состоянии до завоза.

Свободным считается ключ без выдачи и без ЖИВОЙ брони, поэтому истёкшая бронь освобождает товар
сама по себе, даже если фоновая уборка почему-то не отработала.

### Устойчивость покупки

| Действие покупателя | Что мешает сломать покупку |
|---|---|
| двойной клик «Купить» | `Idempotency-Key` с отпечатком запроса: повтор возвращает тот же заказ |
| двойной клик «Оплатить» | ключ оплаты хранится в браузере и определяет `event_id`: событие получается одно |
| обрыв связи в момент оплаты | повтор идёт с тем же ключом, второго платежа не появляется |
| «Назад» после оплаты | страница перечитывает статус с сервера по `pageshow`, а не верит кешу |
| обновление страницы | состояние заказа приходит с сервера, ключ оплаты переживает перезагрузку |
| повторная оплата оплаченного | вебхук отвечает `already_paid`, код и деньги не меняются |

Цена, изменившаяся во время оформления, видна **до** оплаты: заказ отдаёт и зафиксированную сумму,
и текущую цену каталога. Платит покупатель по зафиксированной, а подорожание видит сразу,
в том числе в корзине.

### Мгновенный поиск

Каталог на тысячи позиций (`npm run seed -- --bulk=5000`). Быстро это не только про SQL:

* поиск по подстроке идёт по триграммным индексам (`pg_trgm`) по названию и артикулу;
* наличие берётся из проекции `product_stock`, а не считается по ключам на каждый запрос;
* страницы листаются курсором, а не `OFFSET`, который на глубоких страницах читает и выбрасывает всё до них;
* общее число считается с потолком: разница между «1000+» и «4137» покупателю не нужна,
  а полный подсчёт на широком запросе стоит целой выборки.

На стороне витрины: пауза 150 мс на ввод, отмена предыдущего запроса и номер поколения ответа,
поэтому медленный ответ на старый запрос не перетирает свежий результат. Список заменяется одним
движением и не успевает мигнуть пустотой. Все фильтры лежат в адресе страницы: подборку можно
переслать ссылкой, открыть в новой вкладке и вернуться к ней кнопкой «Назад».
